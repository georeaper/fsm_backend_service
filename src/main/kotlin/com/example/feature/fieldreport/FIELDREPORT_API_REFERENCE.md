# Field Reports API reference

This document describes the Field Reports endpoints registered by the backend and the JSON fields accepted by each one. Routes are registered at the application root, so the paths below are used as written.

## Common requirements

- All endpoints require `Authorization: Bearer <JWT>`.
- The JWT must contain a `databaseName` claim; the authenticated principal also uses `username`.
- Send and receive JSON with `Content-Type: application/json` where a body is used.
- JSON field names are case-sensitive and use the capitalized names shown below.
- `String?` means a nullable string; `Double?`, `Int?`, and `Boolean?` are nullable numbers/booleans. For request models without defaults, nullable fields still need to be present in the JSON (they may be `null`).
- The dates used by the simple create endpoint are `dd/MM/yyyy` (for example, `"06/10/2026"`). GET formats report dates the same way.

## Endpoints

| Method | Path | Purpose | Success response |
|---|---|---|---|
| `GET` | `/fieldreports` | List reports that are not deleted | `200`, array of report objects |
| `POST` | `/fieldreports` | Create one report without child records | `201`, created report object |
| `PUT` | `/fieldreports/{id}` | Update report fields | `200`, submitted report object |
| `DELETE` | `/fieldreports/{id}` | Soft-delete a report | `204`; `404` if not found |
| `POST` | `/fieldreports/bulk` | Create a report and its tools, inventory, equipment, and equipment checkforms | `201`, created report with children |
| `POST` | `/fieldreports/{fieldReportId}/equipments` | Add equipment to an existing report | `201`, created equipment; `404` if report not found |
| `PUT` | `/fieldreports/{fieldReportId}/equipments/{id}` | Update equipment attached to a report | `200`, updated equipment; `404` if not found |
| `DELETE` | `/fieldreports/{fieldReportId}/equipments/{id}` | Soft-delete equipment and its checkforms | `204`; `404` if not found |

Missing JWT/principal or `databaseName` results in `401`. Missing path parameters result in `400`.

## `GET /fieldreports`

No request body. The response is a JSON array; each item has this shape:

```json
[
  {
    "FieldReportID": "report-uuid",
    "RemoteID": null,
    "ReportNumber": "FR-001",
    "Description": "Inspection",
    "StartDate": "06/10/2026",
    "EndDate": "06/10/2026",
    "Title": "Generator inspection",
    "Department": "Maintenance",
    "ClientName": "Client A",
    "ReportStatus": "Draft",
    "Value": 1500.0,
    "LastModified": "06/10/2026",
    "DateCreated": "06/10/2026",
    "Version": "1",
    "CustomerID": "customer-1",
    "ContractID": "contract-1",
    "UserID": "user-1",
    "CaseID": "case-1"
  }
]
```

Fields: `FieldReportID` is a non-null string; `RemoteID` is `Int?`; `Value` is `Double?`; all other fields shown are `String?`. This response does not include `ClientSignature` or child collections.

## `POST /fieldreports` — simple create

Creates only the report row. The request DTO contains the fields below. Include each property; nullable values can be `null`. `StartDate` and `EndDate` must be non-null because the use case force-unwraps them. Use `dd/MM/yyyy`; an invalid date string is converted to `null` by the date parser.

```json
{
  "ReportNumber": "FR-001",
  "Description": "Inspection",
  "StartDate": "06/10/2026",
  "EndDate": "06/10/2026",
  "Title": "Generator inspection",
  "Department": "Maintenance",
  "ClientName": "Client A",
  "ReportStatus": "Draft",
  "Value": 1500.0,
  "CustomerID": "customer-1",
  "ContractID": "contract-1",
  "UserID": "user-1",
  "CaseID": "case-1",
  "isDeleted": false
}
```

`ReportNumber`, `Description`, `Title`, `Department`, `ClientName`, `Status`, `ReportStatus`, `Priority`, `Type`, `CustomerID`, `ContractID`, `UserID`, and `CaseID` are `String?`; `Value` is `Double?`; `StartDate` and `EndDate` are nullable in the DTO but must be supplied with valid dates. `Status` and the legacy `ReportStatus` address the same stored value; when both are supplied, `Status` wins. `Type` stores the selected value from the tenant's `WorkOrderType` settings. `isDeleted` is optional and defaults to `false`; the create use case does not use it. The backend generates `FieldReportID`, audit timestamps, and `Version`.

The `201` response is a report object with `FieldReportID`, `RemoteID`, the report fields, `ClientSignature`, `LastModified`, `DateCreated`, and `Version`. IDs/timestamps/version are generated by the backend; `RemoteID` and `ClientSignature` are initially `null`. It does not include children.

## `PUT /fieldreports/{id}` — update report

All properties in this request shape are required JSON keys by the request DTO, although nullable fields can have a `null` value. `FieldReportID` must be a non-null string in the body, but the path `{id}` takes precedence.

```json
{
  "FieldReportID": "report-uuid",
  "ReportNumber": "FR-001",
  "Description": "Inspection updated",
  "StartDate": "06/10/2026",
  "EndDate": "06/10/2026",
  "Title": "Generator inspection",
  "Department": "Maintenance",
  "ClientName": "Client A",
  "ReportStatus": "InProgress",
  "Value": 1500.0,
  "CustomerID": "customer-1",
  "ContractID": "contract-1",
  "UserID": "user-1",
  "CaseID": "case-1",
  "LastModified": null,
  "DateCreated": null,
  "Version": null,
  "ClientSignature": null
}
```

All fields except `FieldReportID` are nullable. A `null` update value leaves the corresponding regular report field unchanged. The `200` response returns the `EditFieldReportResponse` fields as submitted, with `FieldReportID` replaced by the path ID. If the report does not exist, the repository does not update a row, but this route still responds `200`.

## `POST /fieldreports/bulk` — create report with children

Use this endpoint when submitting the complete report and related records together. The body is a **flat report object** with child arrays on the report itself:

```json
{
  "FieldReportID": null,
  "ReportNumber": "FR-001",
  "Description": "Inspection",
  "StartDate": "06/10/2026",
  "EndDate": "06/10/2026",
  "Title": "Generator inspection",
  "Department": "Maintenance",
  "ClientName": "Client A",
  "ReportStatus": "Draft",
  "Value": 1500.0,
  "CustomerID": "customer-1",
  "ContractID": "contract-1",
  "UserID": "user-1",
  "CaseID": "case-1",
  "Version": "1",
  "isDeleted": false,
  "ClientSignature": null,
  "FieldReportTools": [
    {
      "ToolsID": "tool-1"
    }
  ],
  "FieldReportInventory": [
    {
      "InventoryID": "inventory-1"
    }
  ],
  "FieldReportEquipments": [
    {
      "EquipmentID": "equipment-1",
      "MaintenanceID": "maintenance-1",
      "CompletedStatus": true,
      "FieldReportCheckforms": [
        {
          "Description": "Voltage",
          "ValueExpected": "220V",
          "ValueMeasured": "218V",
          "Result": "OK"
        }
      ]
    }
  ]
}
```

All top-level report properties are optional for this endpoint. The backend generates IDs and default audit fields for the report and its children when omitted. Child collections can be empty or omitted. The response contains the flat report structure and submitted child collections, with generated `FieldReportID`, child IDs, and parent-reference IDs filled in.

### Child object fields

| Object / property | Type | Notes |
|---|---|---|
| `FieldReportTools[]` | object | `FieldReportToolsID: String?`, `RemoteID: Int?`, `FieldReportID: String?`, `ToolsID: String?`, `LastModified: String?`, `DateCreated: String?`, `Version: String?` |
| `FieldReportInventory[]` | object | `FieldReportInventoryID: String?`, `RemoteID: Int?`, `LastModified: String?`, `DateCreated: String?`, `Version: String?`, `FieldReportID: String?`, `InventoryID: String?` |
| `FieldReportEquipments[]` | object | `FieldReportEquipmentID: String?`, `RemoteID: Int?`, `CompletedStatus: Boolean?`, `LastModified: String?`, `DateCreated: String?`, `Version: String?`, `isDeleted: Boolean?`, `FieldReportID: String?`, `EquipmentID: String?`, `MaintenanceID: String?`, `FieldReportCheckforms: FieldReportCheckForm[]?` |
| `FieldReportCheckforms[]` | object | `FieldReportCheckFormID: String?`, `RemoteID: Int?`, `FieldReportEquipmentID: String?`, `Description: String?`, `ValueExpected: String?`, `ValueMeasured: String?`, `Result: String?`, `LastModified: String?`, `DateCreated: String?`, `Version: String?`, `isDeleted: Boolean?` |

`RemoteID` values are integers, `CompletedStatus` and `isDeleted` values are booleans, and the other listed values are strings. In the bulk request, parent/reference IDs can be omitted; the backend assigns them based on nesting.

**Avoid the wrapped payload form** such as `{"fieldReport": {...}, "tools": [...]}`. Although a wrapper DTO exists in the code, the route first decodes the body as a flat DTO while ignoring unknown keys, so a wrapper can be treated as an empty report instead of being unwrapped.

## Equipment subresource

These endpoints accept a `FieldReportEquipment` JSON object. All fields are optional in the request:

```json
{
  "FieldReportEquipmentID": null,
  "RemoteID": null,
  "CompletedStatus": true,
  "LastModified": null,
  "DateCreated": null,
  "Version": "1",
  "isDeleted": false,
  "FieldReportID": "report-uuid",
  "EquipmentID": "equipment-1",
  "MaintenanceID": "maintenance-1",
  "FieldReportCheckforms": []
}
```

`POST /fieldreports/{fieldReportId}/equipments` uses the parent ID from the path and returns the created object with generated ID/audit values. `PUT /fieldreports/{fieldReportId}/equipments/{id}` uses both IDs from the path; it updates equipment attributes and returns the resulting object. `FieldReportCheckforms` is accepted by the DTO but is not saved or updated by these individual equipment endpoints; submit checkforms through the bulk endpoint. `DELETE` has no body.

## Notes for frontend comparison

- Simple `POST /fieldreports` does not save `FieldReportTools`, `FieldReportInventory`, equipment, or checkforms; use `/fieldreports/bulk` for those.
- There are no standalone tools, inventory, or checkform endpoints in this Field Reports route set.
- Report and equipment DELETE operations are soft deletes.
- Field names preserve the backend capitalization exactly (`FieldReportCheckforms` uses a lowercase `f` in `forms`).
# Work Order Technical Cases and Completion

One Work Order can be linked to multiple Technical Cases. The legacy `CaseID` / `TicketID`
field remains available during migration and mirrors the first linked Technical Case.

## Technical Case links

- `GET /fieldreports/{id}/technical-cases` returns the active linked cases.
- `PUT /fieldreports/{id}/technical-cases` atomically replaces the links.

Each returned Technical Case includes `CustomerID` and `CustomerName`. For the selection
list, use `GET /tickets?customerId={workOrderCustomerId}&openOnly=true` so the UI only
presents OPEN cases belonging to the Work Order customer. OPEN is resolved through the
configured `TechnicalCaseStatus.SystemCategory`, not a hardcoded display value. The backend
also rejects cross-customer links and newly-added non-open cases. Already-linked cases remain
visible after completion for history.

```json
{
  "TechnicalCaseIDs": ["tc-uuid-1", "tc-uuid-2"]
}
```

## Complete Work Order

`POST /fieldreports/{id}/complete` accepts the configured closed Work Order status and one
explicit status decision for every linked Technical Case.

```json
{
  "WorkOrderStatus": "Completed",
  "TechnicalCaseUpdates": [
    {
      "TechnicalCaseID": "tc-uuid-1",
      "Status": "Resolved",
      "ResolutionNotes": "Issue fixed during this visit"
    },
    {
      "TechnicalCaseID": "tc-uuid-2",
      "Status": "In Progress",
      "ResolutionNotes": "A replacement part is required"
    }
  ]
}
```

When linked cases exist but `TechnicalCaseUpdates` is empty, the API returns `409` with
`code = CONFIRM_TECHNICAL_CASE_STATUS_CHANGE` and the linked cases. The UI should use this
response to show the confirmation/status-selection dialog and then retry the completion.
Statuses are validated through `TechnicalCaseStatus` / `WorkOrderStatus` settings and their
`SystemCategory`; no display value is hardcoded as the closed status. When `ResolutionNotes`
is provided, it is stored both on the Work Order–Technical Case link and as the current
`Description` of that Technical Case. The previous description is preserved in `ticket_history`.

## Technician assignments

- `GET /fieldreports/{id}/technicians` lists active assignments.
- `PUT /fieldreports/{id}/technicians` atomically replaces assignments.

```json
{
  "Technicians": [
    { "UserID": "user-1", "Role": "LEAD" },
    { "UserID": "user-2", "Role": "ASSISTANT" }
  ]
}
```

Roles are `LEAD` and `ASSISTANT`, a user can appear once, and at most one active Lead is
allowed. `FieldReports.UserId` temporarily mirrors the Lead for backward compatibility.

## Scheduling calendar

```http
GET /scheduling/workorders?from=20261001000000&to=20261031235959
GET /scheduling/workorders?from=20261001000000&to=20261031235959&technicianId=user-1&status=Planned
```

Only Work Orders with both `ScheduledStart` and `ScheduledEnd` are returned. Calendar events
include customer, `Type`, `TypeColor`, and all technician assignments. `TypeColor` comes from
the matching `WorkOrderType.SettingsStyle`, so calendar colors follow settings changes without
a frontend hardcoded mapping. Scheduled values accept `yyyyMMddHHmmss` or
`dd/MM/yyyy HH:mm:ss`; both values are required and end must be after start.
The date range cannot exceed 366 days. The endpoint also accepts `page` and `pageSize`
(default `1`/`50`, maximum page size `200`) and returns pagination metadata in `X-*` headers.
